# Atlas vs llama.cpp performance gap analysis

Root-cause analysis of why llama.cpp outperforms Atlas on the matched
benchmark, based on `artifacts/atlas-vs-llama/` and
`artifacts/profiles/atlas-profile.json`.

## TL;DR

On the same GGUF, the same `q4_0` KV cache, and the same Apple M2 Max, Atlas is:

- **12–45× slower at prefill** (the gap grows with prompt length);
- **2–5× slower at decode** (the gap grows with context).

Two structural causes explain almost all of it:

1. **Prefill re-reads weights per token instead of running one batched GEMM.**
   llama.cpp processes all prompt tokens as a single batch (`n_ubatch=512`), so
   every weight tensor is read from memory once for the whole prompt. Atlas
   slices the prompt into 128-token chunks and then loops per token through
   qk-norm/rope, attention, RMS, and KV-append kernels (~164 dispatches/token).
   This is why the prefill gap *grows* with prompt size while llama.cpp's
   prefill stays flat (~1600 tok/s).
2. **Decode is dispatch/occupancy-bound, not bandwidth-bound.** Atlas launches
   ~550 dispatches/token with ~34k threadgroups/token, landing at ~8.7× the
   pure weight-read bandwidth floor. llama.cpp runs ~2.1× the floor, i.e.
   close to memory-bound. Atlas's GPU spends its time on small-kernel launch
   latency and occupancy gaps rather than saturating memory.

## Root causes

### 1. Prefill: batched GEMM vs per-token loops

llama.cpp (`-p 512 -n 128`, defaults `n_batch=2048`, `n_ubatch=512`) treats the
entire prompt as one micro-batch. For each weight tensor it issues one
matrix multiply with `M = number of prompt tokens`, so each weight is fetched
from DRAM **once per layer**. That is why llama.cpp prefill stays at
~1600 tok/s from pp100 to pp1024.

Atlas prefill uses `prefill_chunk_size = min(prompt_tokens, 128)` and, inside
each chunk, executes per-token dispatch loops for qk-norm/rope, attention,
RMS, and KV-append. Every dispatch re-reads the same weights and pays full GPU
launch latency. Prefill therefore scales as (prompt tokens × dispatch cost)
instead of (weights read once + attention over the batch). This is the primary
explanation for the 12×→45× prefill gap and for why it grows with prompt size.

### 2. Decode: small-kernel decomposition vs fused kernels

Atlas decode launches ~16 kernels per layer per token: RMS, qk-norm+rope, QKV
matvec, attention, KV-append, attention-output, residual, gate/up, gelu,
ffn-down, PLE, final norm. Each is a small Metal compute dispatch (~34k
threadgroups/token). At 8.7× the bandwidth floor the GPU is latency-bound:
dispatch setup, occupancy ramp, and small-kernel turnaround dominate wall time.

llama.cpp's Metal backend fuses RMS into the consuming matvec, fuses
activation, and uses vectorized flash attention, so it issues far fewer,
larger dispatches and sits near the bandwidth bound.

### 3. Attention degrades with context in Atlas

Atlas decode drops 41→19→16 tok/s as the prompt grows 100→512→1024 because
decode runs at the *full* prompt context (attention cost over N KV entries).
llama.cpp decode stays ~80 tok/s in this benchmark because llama-bench's `tg`
test decodes from empty context (see caveats); at matched context the real
llama.cpp decode is slower than 80 tok/s, but its attention kernel is still
substantially cheaper than Atlas's per-slice KV scan.

## Measurement caveats

- llama-bench `tg` decodes from **empty context** (`n_prompt=0`; ~80 tok/s
  regardless of `-p`), while Atlas decodes at the full prompt context. The
  decode ratios therefore **overstate** the gap; the honest decode gap is
  ~2× at short context and grows with context.
- Prefill numbers are apples-to-apples (both engines process exactly N prompt
  tokens).
- Both engines used the same GGUF file and `q4_0` KV cache
  (`-ctk q4_0 -ctv q4_0` for llama-bench).
- llama.cpp `n_batch`/`n_ubatch`/`n_threads` and Atlas prefill chunking were
  not forced to identical values; the comparison uses each engine's defaults.
- Hardware: Apple M2 Max, macOS. Model revision
  `675cff42a74c774d6cb76f76d8eacb49b48c9b93`.

## Recommendations (priority order, with concrete solutions)

Each recommendation names the exact code that must change and what the
replacement should look like, so it can be executed directly.

> Status 2026-08-12: **R1 is implemented** (phase-13.1) — prefill is ~200
> tok/s flat across prompt sizes with a byte-identical greedy stream. **R2 is
> already in production.** The remaining decode gap is covered by the
> dedicated [Decode improvement recommendations](#decode-improvement-recommendations-measured-2026-08-12-phase-132)
> section below (D1–D4).

### R1 — Batch the remaining per-token prefill kernels (highest priority)

**Problem (the 12–45× gap).** The matmuls are already token-batched
(`matmul_q4_0_batch_16row`, grid = `batch × width/16`), but four kernels are
still dispatched inside `for token in 0..batch_value` loops in
`Gemma4E2bExecutor::encode_prefill_layer_major_layer`
(`crates/atlas-model/src/gemma4_executor.rs:3120-3194`):

- `gemma4_qk_norm_rope_fused_f32` (line 3124),
- `rms_norm_groups_in_place_unweighted_f32` (line 3144),
- the KV-append kernel (line 3160),
- the attention kernel (line 3176).

That is ~4 dispatches/layer/token × 35 layers ≈ 140+ of the ~164
dispatches/token. Every dispatch re-reads the same weights and pays full GPU
launch latency, which is why prefill degrades with prompt length.

**Suggested solution for Atlas.** Add a token dimension to the grid of those
four kernels so one dispatch covers the whole chunk:

1. `gemma4_qk_norm_rope_fused_f32` (`crates/atlas-metal/src/kernels.metal:619`):
   change grid from `q_heads + has_key` to `batch × (q_heads + has_key)`, map
   `group = token × heads + head`, and offset every buffer by
   `token × width` (a `token` buffer argument, like `batch` already passed to
   the matmuls). One threadgroup per (token, head) preserves the exact
   per-token RMS/RoPE math.
2. `rms_norm_groups_in_place_unweighted_f32` (kernels.metal:535): grid =
   `batch × groups`, offset the V pointer by `token × head`.
3. KV-append (kernels.metal:697): grid = `batch × blocks`, offset key/value and
   cache by `token × width` / `position` per token.
4. Attention (kernels.metal:986 or the Flash16 exact variant at :1030): grid =
   `batch × heads`, offset `q_rot`/`attention` by `token × q_width` and read
   `key_control` from the per-token control table already built
   (`forward_tokens_layer_major` writes `key_counts` per token × layer).

Also raise the prefill batch cap from `GEMMA4_PREFILL_BATCH_CAPACITY = 128`
(`gemma4_executor.rs:23`) and `Gemma4PrefillPlan::new`'s
`prompt_tokens.min(128)` (`gemma4_executor.rs:681`) to 512 to match llama.cpp's
`n_ubatch=512`, so a pp512 prompt is one chunk instead of four.

**Expected impact.** Prefill dispatches drop from ~164/token to a handful per
chunk; weights are read once per layer. Prefill ~36–50 tok/s →
several hundred tok/s, closing most of the dominant gap. Keep a kernel-level
tolerance test (max-abs < 1e-3 vs the current path) per new batched kernel,
mirroring `batch_matmul_parity.rs`.

### R2 — Promote the RMS-into-matvec fusion to production default

**Problem.** Decode still launches a standalone RMS dispatch per layer
(`rms_norm_decode_f32_vec4`, ~264 dispatches/token), each re-reading and
re-scaling the full 2304-wide hidden buffer — a compute-trivial kernel that is
launch/latency-bound.

**Suggested solution for Atlas.** Make the four `_rms` kernels
(`matvec_q4_0_64row_mv_rms`, `matvec_q6_k_64row_mv_rms`,
`matmul_q4_0_qkv_32row_mv_rms`, `matmul_q4_0_gate_up_32row_mv_rms`) the
production default for decode by removing the
`ATLAS_GEMMA4_RMS_MATVEC_EXPERIMENT=fused` opt-in gate
(`gemma4_executor.rs` decode path, `matmul_q4_0_qkv` / `matmul_q4_0_gate_up` /
`matvec_labeled` call sites). Phase 13.0 P1/P2c already implemented and parity-
proven these (`matvec_rms_fused_parity.rs`, max-abs ~1e-8); the composed stack
just needs to become unconditional.

**Expected impact.** Removes ~264 dispatches/token plus hidden-state round
trips; several percent of decode, larger share of host-encode.

### R3 — Cut decode dispatches from ~550/token toward ~180/token

**Problem.** Decode runs ~16 kernels/layer/token (RMS, qk-norm+rope, QKV, KV-
append, attention, attn-out, residual, gate/up, gelu, ffn-down, residual,
PLE…), the core of the 8.7×-floor latency binding.

**Suggested solution for Atlas.** Fusion is already partially done
(`gemma4_rms_residual_f32`, `gelu_multiply_f32`,
`ple_gelu_multiply_offset_f32`, `kv_append_decode_q4_0_vnorm`). Close the
remaining gap to ~5 dispatches/layer/token:

- RMS-QKV: already fused (`matmul_q4_0_qkv_32row_mv_rms`).
- RMS-gate/up + gelu: already fused (`matmul_q4_0_gate_up_32row_mv_rms` +
  `gelu_multiply_f32`).
- attn-out + post-attention RMS + residual: `gemma4_rms_residual_f32` covers
  the RMS+add; fold the attn-out matvec epilogue into it.
- ffn-down + post-FFN RMS + residual: extend the same `gemma4_rms_residual_f32`
  site (P2c pattern) to the FFN matvec.
- qk-norm+rope→attention: **skip** — P2d measured the Q-side fold at <0.3% at
  512 context and the K-side is blocked because attention reads the quantized
  cache while K-norm+rope runs on raw K.

35 layers × ~5 fused dispatches ≈ 175/token + fixed overhead ≈ ~180/token, a
3× reduction from 550. Combine with batching multiple decode tokens' dispatch
*encoding* into shared command buffers (already the model; the win is fewer
kernels, not more CBs).

**Expected impact.** 10–30% decode; every removed dispatch also cuts
host-encode (the ~16% cpu-encode component).

### R4 — Vectorize the attention KV scan (context scaling)

**Problem.** Atlas decode drops 41→19→16 tok/s as context grows because the
attention kernel (`DEFINE_FLASH16_EXACT`, kernels.metal:1030) scans keys
serially in a per-slice loop, re-reading the KV range per slice.

**Suggested solution for Atlas.** Keep the exact FP32 accumulation order (the
`_flash16_exact` requirement is non-negotiable for greedy parity), but stage
key blocks through threadgroup memory so each key block is read once per
threadgroup instead of once per slice. Phase 13.0 P3 was blocked on the 32 KiB
budget for the *value* merge; a wider-visibility redesign with single-writer V
accumulation (one SIMD group owns a V half while the score reduction covers
the full key range) is the path, verified by `attention_flash_correctness.rs`
and the exact-stream gate.

**Expected impact.** Attention cost stops growing with context; matters at
8k+ context, low value at the 512-token gate.

### R5 — Matvec bandwidth saturation (do last, only combined with R2/R3)

**Problem.** The 64-row matvec family (P4) cut threadgroups by 18% but moved
GPU time only ~1% — the kernel is not launch-bound.

**Suggested solution for Atlas.** Do not tune row counts further. The real
fix is fewer, larger dispatches: fold RMS in (R2), fuse epilogues (R3), and
let the bandwidth floor become the limit. Re-measure with
`profile bottlenecks` after R2/R3 before any further matvec work.

**Expected impact.** Closes part of the 2.1×→8.7× floor distance, but only in
combination with R2/R3.

## Decode improvement recommendations (measured 2026-08-12, phase 13.2+)

Status as of phase-13.3 (D1 + D2 landed): prefill is ~200 tok/s flat across
prompt sizes, and decode attention is now the staged exact-ordered v3 kernel
(D2, −12.7% decode GPU at pp512) on top of the no-value-barrier default (D1,
−8.6%). **Decode is the remaining gap** — ~24.0 tok/s at the matched pp512
workload (was 19.6 at phase-13.1 / 21.4 at phase-13.2). This
section re-measures the decode baseline and prioritizes the concrete work,
superseding the generic R2–R5 ordering for decode.

### Measured: Flash16-exact is not a decode win by itself

Switching the q4 attention from `attention_decode_fused_gemma4_simd_q4_0`
(LegacyFused) to `attention_decode_gemma4_simd_q4_0_flash16_exact_runtime`
moves decode GPU 6443 → 6402 ms (19.79 → 19.74 tok/s), i.e. no material
delta, with the greedy stream hash unchanged (`f23c2962…`). The exact kernels
deliberately preserve LegacyFused's per-key serial scan and value barrier, so
they are parity-equivalent by design, not faster.

### D1 — Default the q4 attention to the no-value-barrier flash16 variant

> Status 2026-08-12: **D1 is implemented** (phase-13.2). Default is now
> `Flash16` (`attention_decode_gemma4_simd_q4_0_flash16_exact_nb` /
> `_swa_exact_nb`). Decode GPU 6455.1 → 5900.5 ms/128 tokens (−8.6%) at the
> matched pp512/tg128 workload with a byte-identical greedy stream
> (`f23c2962…`); per-token fp32 logit-digest and exact-token parity gates pass.
> Evidence under `artifacts/phase-13.2/`.

**Problem.** The production default (`LegacyFused`) and the
`_flash16_exact_runtime` binding both hold a `threadgroup_barrier` after every
key's value update. `attention_decode_gemma4_simd_q4_0_flash16_exact_nb`
removes only that redundant barrier (same four-SIMD reduction, same
key-ordered online softmax); phase-13.0 and commit 3da8bb9 measured ~8% decode
GPU from it.

**Suggested solution.** Gate on `flash16_matches_legacy_resident_output_logit_digests`
(ignored, per-token FP32 logit digests) and the exact-token stream, then flip
`Gemma4Q4AttentionMode::default()` to `Flash16` and point
`gemma4_q4_flash16_binding` (`crates/atlas-model/src/gemma4_executor.rs:420`)
at `attention_decode_gemma4_simd_q4_0_flash16_exact_nb` /
`_swa_exact_nb` (already registered in `kernels.metal:1085-1086`).

**Expected impact.** ~8% decode GPU, zero risk to greedy parity.

### D2 — Vectorize the attention KV scan (R4, the largest lever)

> Status 2026-08-12: **D2 is implemented** (phase-13.3). The default q4 decode
> attention is now the staged, chunked v3 kernel
> (`attention_decode_gemma4_simd_q4_0_flash16_exact_v3` /
> `_swa_exact_v3`) with wide threadgroups (512 full / 256 swa per head):
> three barrier-separated passes per 128-key chunk (score → fold/online-softmax
> → register-resident value chain) eliminate the ~2 per-key threadgroup
> barriers and the per-key device output round trip while preserving
> LegacyFused's exact FP32 order byte-for-byte, and the wide launch keeps
> several independent key chains in flight to hide KV memory latency. Decode
> GPU −31.6% at the matched pp512/tg128 workload (5900.5 → 4034.6 ms/128
> tokens, 21.4 → 31.0 tok/s) with a byte-identical greedy stream
> (`f23c2962…`); decode is 53.6/31.0/27.4 tok/s at pp100/512/1024 (was
> 41/19/16). The `_nb` kernel stays reachable via
> `--q4-attention-mode flash16_exact`. Evidence under
> `artifacts/phase-13.3/`.

**Problem.** The dominant cost. Both attention kernels scan keys serially with
a per-key threadgroup barrier and online-softmax value update, re-reading the
KV range per slice; cost grows with context (decode 41→19→16 tok/s at
pp100→512→1024).

**Suggested solution.** Keep the exact FP32 accumulation order, but stage key
blocks through threadgroup memory so each block is read once per threadgroup
instead of once per slice, with single-writer V accumulation (one SIMD group
owns a V half while the score reduction covers the full key range). Phase-13.0
P3 was blocked on the 32 KiB budget for the value merge; the wider-visibility
redesign is the path. Verified by `attention_flash_correctness.rs` and the
exact-stream gate.

**Expected impact.** Attention stops growing with context; largest single
decode win at 512+ context.

### D3 — Cut decode dispatches from ~552 to ~180/token (R3, refined)

**Problem.** 547.7 dispatches/token ≈ 16.3/layer/token is the latency binding
behind the 8.7× floor distance; host-encode is ~2.1 ms/token (~16%).

**Suggested solution.** Fusion is already partially in production (R2 landed:
`matmul_q4_0_qkv_32row_mv_rms`, `matmul_q4_0_gate_up_32row_mv_rms`,
`gemma4_rms_residual_f32`, `gelu_multiply_f32`). Close the rest:

- **PLE (106 disp/t)**: batch or fuse the three per-layer PLE matvecs
  (`matvec_labeled` on `inp_gate`, `projection`, and the per-layer model proj)
  and the PLE norm; mirror the prefill batched-PLE pattern from R1.
- **attn-out + post-attention RMS + residual**: fold the attention-output
  matvec epilogue into `gemma4_rms_residual_f32`.
- **ffn-down + post-FFN RMS + residual**: extend the same
  `gemma4_rms_residual_f32` site to the FFN matvec.
- **qk-norm+rope → attention**: skip (P2d measured Q-side <0.3%; K-side
  blocked because attention reads the quantized cache while K-norm runs on raw
  K).

**Expected impact.** 10–30% decode plus most of the host-encode component;
35 layers × ~5 fused dispatches ≈ ~180/token.

### D4 — Do not tune matvec breadth further (R5)

The 64-row family cut threadgroups 18% but moved GPU ~1%. Re-measure only
after D1–D3; the floor becomes the limit when the small-kernel overhead is
gone.

**D1 first** — ~8%, parity-proven, one-line binding change. **D2** when

### Execution order (overall)

**R1 (landed, phase-13.1)** — batched prefill kernels; prefill 49.6 → ~200
tok/s at pp512 with a byte-identical greedy stream. **D1 (landed,
phase-13.2)** — q4 attention defaults to the no-value-barrier flash16 kernel,
